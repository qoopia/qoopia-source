# Connecting and recovering MCP

## Standard path

Open Connections in the dashboard of the selected installation or the installed `qoopia connections`. Read `qoopia help` and `connections-agent.md` of exactly this package. Do not substitute a demo or development address for the user's memory.

Plan first: the selection JSON contains surface (`chatgpt_web`, `chatgpt_desktop`, `claude_web`, `claude_desktop`, `codex`, `claude_code`, `muse_code`, `muse_app`, `grok_bot`), access_mode (`read` or `read_write`) and a stable request_key. transport is auto/local/remote depending on the context. Commands: `connections plan --input ABSOLUTE_JSON`, then the authorized `connections apply --input ABSOLUTE_JSON --commit`. Use the returned IDs and the exact MCP URL; do not assemble them by guesswork. Muse Code is configured in the user's settings.json and signs in with `muse mcp login`; the cloud Grok Bot receives the exact remote MCP URL in a request to add a connector. A record or OAuth existing does not prove that it works: call `qoopia_protocol` from the selected client after OAuth. The server automatically confirms the first successful protocol read through the client's exact connection. Automatic session saving is not set up separately for these clients yet.

A cloud client needs an installation reachable from outside. The standard network-plan/network-start/network-resume carry out registration and the user's sign-in. Prepare the email/google method according to the current schema. The service/tunnel must be running; localhost on a Mac is not reachable from Claude.ai or ChatGPT in the cloud.

## Different clients

- Codex: client-plan/client-apply or client-link prepare a separate entry in the selected CODEX_HOME/config.toml. Keep the other servers and the model. The user authorizes exactly this entry; a new session then reads AGENTS.md or the effective AGENTS.override.md. The managed block links to qoopia-protocol.md.
- Claude Code: use the selected CLAUDE_CONFIG_DIR, the standard configuration and /mcp to sign in. CLAUDE.md imports qoopia-protocol.md. Do not confuse the user profile with the .mcp.json of an arbitrary project. For automatic session saving use memory-link and its standard hooks, not copies of someone else's hook files.
- Claude Desktop: the standard local adapter/client-auth on macOS, then restart the application. Removing the entry from the JSON does not revoke the OAuth grant. The application does not have to read the local CLAUDE.md: get the protocol through the MCP qoopia_protocol and, if needed, add it to the instructions of the selected project.
- Claude.ai: set up the remote MCP connector the user is allowed to use in the Claude interface, and complete the user's OAuth to the exact prepared URL. Local AGENTS.md/CLAUDE.md do not reach the browser by themselves. The protocol is available through the qoopia_protocol tool; pin an instruction to read it in the selected project/conversation if the client has this feature.
- ChatGPT Web/Desktop: use the official apps/connectors/developer mode interface for custom MCP available in the account. Capabilities depend on the client, the plan and organization policies; if the interface is missing or the client blocks the check, record BLOCKED. The last check with a real client (ChatGPT Pro, Web and Desktop on Mac) passed on 15 September 2026; the current consent and automatic connection confirmation have not been re-checked with a real ChatGPT account. Do not work around a client restriction with another surface and do not call a Codex task a check of a ChatGPT chat. Read qoopia_protocol through the selected connector; for lasting behaviour pin the protocol in the project instructions available. A local file is not considered automatically installed in a cloud account.

## Verification and reconnection

1. First connections status/resume for the existing ID. Use the ready request from the connection card; it contains no temporary code.
2. From the selected client, call qoopia_protocol through its exact MCP URL. After a successful call the server confirms the connection and the dashboard updates the status automatically. Configuration, OAuth and tools/list do not confirm that it works by themselves. A separate verify operation with a one-time challenge remains for compatibility; an ordinary user does not need it.
3. When a sign-in simply expires, re-authorize the existing connection; do not create an extra agent. SIGN_IN_REQUIRED during network registration requires a new network-start and the user's consent.
4. On CLIENT_CONFIG_MISSING use client-plan/client-apply. On CLIENT_CONFIG_CHANGED/CONFLICT keep the user's edit; do not overwrite the configuration. First agree on restoring that specific entry.
5. A revoked connection cannot be revived by editing a token or SQL. Create a new one with a new request_key after choosing the previous workspace and the scope needed; check it with a real call. Remove the old local entry only with the standard client-remove with a receipt. Do not remove other MCP servers.
6. If a profile is moved, choose config_directory/--config-directory explicitly. A binding saved earlier must point to the same profile. Do not edit native_root by hand and do not copy OAuth/hooks between profiles. `memory-link --file` without `--commit` only shows a plan (address, client, plan_digest) and writes nothing; apply `--commit --approve PLAN_DIGEST` with the same file and profile only after the owner has confirmed the address is their own Qoopia. Running memory-link again for the same server after the agent is reissued or its key changes replaces the previous binding (hooks, the `qoopia_memory` entry, the connection file) with backups; it leaves an entry edited by hand alone.
7. A refusal of the local instructions (an `INSTRUCTIONS_*` code and a file path in `protocol`) does not block the MCP entry: the protocol is available through qoopia_protocol. Fix the named file and repeat client-apply or memory-link. A Qoopia block removed by hand is not brought back by the hook or `instructions refresh`; only an explicit client-apply or memory-link adds it.
8. Disconnecting without manual edits: `memory-unlink --runtime codex|claude_code --commit` removes the memory-link hooks, the `qoopia_memory` entry with its key and the managed block; `instructions remove --runtime codex|claude_code --commit` removes the block and the unchanged documents. Without `--commit` this is only a plan. Other people's hooks, servers and the owner's text are kept; anything changed is refused. Revoking the agent in Qoopia is a separate action.
9. Check the protocol in a new session: the agent must name the source of its instruction and its version. Check read; check writing only with permitted test content. With read scope, writing is neither required nor permitted.

Updating the instruction does not change MCP scopes, does not grant the owner role and is not a successful connection. Keep the report item by item: config installed, user authenticated, protocol available/loaded, MCP verified, memory read/write, session capture/summary/restore.


## Steward onboarding: prepare it and see it through to a real call

- First check the current `qoopia_capabilities` and the existing identity. Do not rename FIBI to Phoebe and do not create a duplicate of an agent that is already connected.
- If `connection_prepare` is available, pass the exact `agent_name`, `surface`, `access_mode`. To correct the label of an existing connection, pass its `connection_id`. This is a read: the tool creates no keys, agents or OAuth grants. Give the owner one link, `owner_url`, not a JSON instruction.
- The owner opens the prepared form, checks the name, the application and the permissions and presses "Prepare connection". The link parameters do not confirm consent and grant no access. The application receives the exact MCP URL from this record. For an active connection the form opens its card: "Save name" keeps the ID, OAuth, notes and confirmation; the classification can only be corrected between Muse.app and Muse Code CLI.
- `muse_app` is a cloud agent in Muse.app (for example FIBI); the Mac application is an interface, not where it runs. `muse_code` is a separate terminal client. The `muse mcp login` commands and its `settings.json` do not configure Muse.app.
- For Muse.app use "Copy request": it includes the setup and reading the protocol through the same MCP URL, without a temporary verification code. Use the MCP client that the cloud runtime supports. Do not promise a built-in screen for arbitrary MCP: that needs a separate check. If the client has no safe OAuth path, name exactly that obstacle; do not suggest a broken localhost callback with the code copied into the chat. Secrets and OAuth codes are not passed through the conversation.
- Get the protocol and capabilities from the target client itself. The request must name the exact MCP URL of the selected connection. For read_write, separately check a permitted synthetic write, a read and a repeat with the same idempotency key. MCP access and automatic saving of the whole conversation are checked separately.
- If the preparation tool is missing, read the current connections section through `qoopia_protocol`; do not present a tool that is not installed yet as available. Keep the goal and the exact existing ID for the owner's standard form; do not raise your own permissions.

In the same browser, the owner's active session is used for OAuth consent without another email. Consent to the permissions of each new client stays explicit. If there is no owner session, an ordinary sign-in is needed. Another account, an agent session and an agent's OAuth token do not replace the owner's session.
