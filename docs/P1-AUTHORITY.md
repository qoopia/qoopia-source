# P1 authority: implementation and boundaries

This document describes the implemented P1 boundary. Acceptance status and actual execution results are in `../P1-EVIDENCE.md`. P2/P3 operations are not enabled by the P1 capability catalog.

## Authority and callers

The existing Qoopia `workspaces`, `agents` and `entity_pages(type=skill)` retain canonical identity. Migration 036 adds explicit human-owner association, principal profiles and authentication epochs. An old `type=owner` or administrator token does not establish human identity. After explicit migration to the current schema, `qoopia owner bootstrap --name <new-human-name> --workspace-name <name>` creates the first workspace and a separate human owner. For an existing ownerless workspace, the local operator must instead specify `--workspace-id <existing-id>` (inspect IDs with `qoopia admin list-workspaces`). The CLI requires the database owner's OS UID, rejects setuid execution and read-only instances, and returns the new owner API key once in its command output. Keep that output private. It never promotes an existing agent, replaces an owner or accepts a remote bootstrap/claim. A transaction makes concurrent claims single-use. Processes with arbitrary file/memory access under the same OS user are outside this boundary (§10.2); browser onboarding and owner recovery remain P3.

In-place schema35→36 migration preserves old skill API eligibility as `legacy_skill_access`, separate from canonical author permissions. Every call intersects eligibility with the current active principal, tool profile, OAuth scope, authentication generation, instance role and reporter exclusion. Old `full` and `no-destructive` profiles retain write-low rights for every old agent type; `read-only` never gains writes. Migration does not promote any principal to skill-author or human owner. The legacy `createAgent` entry point preserves this same compatibility eligibility; new P1 pairing and imported principals default to no legacy grant. Removing eligibility increments the policy epoch. Migration logs one non-secret permission mapping per old principal after commit, with token-specific scope explicitly left to runtime enforcement.

Legacy skill identities keep their original immutable revision and provenance actor. Eligible old callers can append revisions across the workspace as before; they cannot take over a new canonical draft without canonical draft authorization and edit rights. Revisions record the actual caller, and legacy edits never change frozen package bytes. Legacy callers still need the P1 retry key and expected revision. The fresh-install and source35 execution regressions are `tests/p1-owner-upgrade.test.ts`; they use real CLI processes and MCP SDK transports without listening sockets.

`src/auth/policy.ts` resolves current DB authority on every command, including replay. `currentToolAuth` is shared by the existing MCP and compatibility dispatchers; reporters cannot call general memory/admin tools. An explicit empty OAuth scope array denies access. For legacy memory/compat tools only, absent scopes (SQL NULL or empty stored text under ADR-017) fall back to the current DB tool profile. Canonical P1 operations require explicit OAuth grants; legacy fallback cannot create new P1 or human-owner authority. An agent's profile and workspace are never accepted from an external skill payload. Scoped signing-key registration accepts public keys only. Pairing codes expire after ten minutes, redeem once, and never appear in command receipts. Issuance replay returns recovery instructions instead of the earlier secret. Imported principals are inactive and require fresh enrollment.

Draft writes flow from REST, MCP, CLI, `skill_upsert`, and generic `entity_upsert(type=skill)` to `reviseDraft`. No legacy skill SQL writer remains. Command responses use the same persisted canonical representation on initial success and replay, so ordinary mutation results have identical serialized JSON across MCP, REST and CLI; one-time enrollment secrets still follow their separate no-replay rule. Stable entity IDs survive rename; forks get a new identity with an explicit parent. Revision rows and frozen versions have SQL immutability constraints. Expected revision protects the head; stale responses preserve the submitted edit. Reviews have their own decision revision. Only the latest eligible decision can authorize sealing or consent use.

A content review does not grant high-risk adoption. `requireExactConsent` binds the current human owner's decision to sealed package/version, target principal, runtime registration UUID, target scope, capabilities, operation, expiry and policy epoch. An API field named `runtime_id` in this consent schema means the registration UUID returned as `runtime_registration_id` at enrollment, not the runtime's display label. Actual assignment/adoption and runtime execution are P2.

## Typed surfaces

The authoritative schema/handler registry is `src/api/authority.ts`; generated per-profile JSON Schemas are in `artifacts/p1/catalog.json`. REST paths have the `/api/v1` prefix. The HTTP listener delegates to that registry. REST-handler tests use real Request/Response objects; they are not claims of a working socket listener in this environment.

| Operation | REST suffix | CLI |
|---|---|---|
| Discovery | GET `/capabilities` | `capabilities` |
| Enrollment | POST `/agent-pairings`, `/agent-pairings/redeem` | `pairing create`, `pairing redeem` |
| Revoke | POST `/principals/:agent_id/revoke` | `principal revoke` |
| Public signing key | POST `/publisher-keys` | `publisher-key register` |
| Draft | POST `/skills/drafts`, PATCH `/skills/drafts/:draft_id` | `skill revise` |
| Compile | POST `/skills/drafts/:draft_id/compile` | `skill compile` |
| Review / seal | POST `/skills/candidates/:version_id/reviews`, `/seal` | `skill review`, `skill seal` |
| Read | GET `/skills`, `/skills/:id`, `/skills/:id/versions/:version_id`, `/skills/:id/runbook` | `skill search`, `skill get`, `skill runbook` |
| Receipt | GET `/operations/:id` | `operation get` |

CLI named operations use `--input <json-file>` and scoped `QOOPIA_API_KEY`. Pairing redemption authenticates by the one-time code. Mutation schemas require `idempotency_key` and `expected_revision` or `expected_digest`; REST also requires matching `Idempotency-Key` and `If-Match` headers. Review requires its decision revision in the body as well as the candidate digest precondition. Creation uses revision 0. Fields are closed; unknown fields and mismatched identities are rejected. The catalog contains the exact shapes and current limits. Human enrollment/key administration is intentionally absent from the MCP agent catalog.

MCP uses the same named handlers and machine-readable errors. Existing generic SDK `call` methods can call those names with the published schema; this change does not introduce an untyped universal tool. Normal bootstrap discovery is profile filtered; an explicit full compatibility connection keeps authorized legacy discovery. Existing note/session/extraction/AgentComm transports and services remain in place; this patch does not claim to implement every future REST route in master §8.2.

Legacy skill mutation clients must now supply expected revision and idempotency key. This is an explicit safety compatibility delta, not transparent compatibility with old unmodified writers. `skill_mark_tested` records an authenticated, revision-bound self-report; it never forges independent verification or rewrites a signed artifact. Historical P05 snapshots remain frozen. `scripts/v4-contract-snapshot.ts --check --p1` checks only this declared delta and compares the remaining surface with those snapshots. No actual sunset build was executed: release age, two subsequent minor releases and caller migration remain required. No zero-production-callers claim is made.

## Frozen package encoding

`qoopia-skill-package/1` is UTF-8 JCS, with no BOM, trailing newline or trailing bytes. Its closed envelope contains `format`, `signature_profile`, `descriptor`, `members`, `signature`. Member bodies use canonical base64; the descriptor commits to exact member names, decoded sizes and SHA-256 hashes, version label, license, compiler/renderer, compatibility, requested capabilities and secret-reference names. Source/private provenance is not a portable member by default.

`candidate_digest = SHA256(JCS(descriptor))`; `content_digest = SHA256(JCS({compiler_version,content}))`; `package_digest = SHA256(exact envelope bytes)`. The detached signature payload is `{profile:"qoopia-skill-signature/1",descriptor}`. Signing uses the unchanged original Skillonomia JCS/Ed25519/JWS primitive on that separate profile. Sealing receives a detached publisher signature, validates the registered current public key and approvals, and freezes the package in the same SQLite transaction. It does not load a production private key.

`tests/fixtures/p1/package-v1.json` and its digest manifest freeze the new byte encoding. Original TV-01 vectors and the legacy signing profile are kept separately. `src/skills/legacy/PROVENANCE.json` records exact copied-file hashes and source SHA; the original license accompanies those files. No new package dependencies were introduced.

Archive handling preserves the original legacy limits (512 members, 4 MiB per member, 64 MiB total, 100:1 gzip ratio) and adds an aggregate nested budget with depth 3. Parsing never extracts to a native root or executes members. Existing secret guard runs over structured content, portable descriptor and added text members; it is not a guarantee that every possible secret can be recognized.

## Migration adapters and bounded compromises

`preflightSource` / `importSource` accept explicit immutable SQLite snapshot bytes and original blob bytes. Supported manifests are Qoopia 32/35 and Skillonomia 19. Schema 10, unknown tables/columns, missing blobs, bad signatures/tlog, raw WAL files, missing workspace mappings and inconsistent foreign keys stop the import. Qoopia 32 temporal normalization runs the existing 033 preflight/gate/apply on an in-memory working copy. Original source rows remain immutable, including original timestamps, IDs, digest/compiler fields and BLOB bytes.

Each source row gets an origin-instance/type/id mapping. Same-ID or slug collisions allocate separate local identities and report the collision. The archive preserves fields that are not live P1 models. Old signing keys and replay tables are historical data, not active credentials or new authorization. Skillonomia signed-only versions are readable canonical identities without inventing a draft. Historical approved native revisions preserve exact original content bytes. Assignments, loadouts, observations, outcomes, grants and transport receipts are retained in an immutable paused archive for the P2 importer, not advertised as active P1 runtime state.

The P1 adapter uses one atomic transaction per source, bounded to 256 MiB snapshot and 100,000 rows per canonical table. Resume/repeat is bound to source+blob digest, explicit workspace mapping digest and supplied build SHA; changed inputs refuse rather than silently adopting a winner. Ambiguous global rows in a multi-workspace source require an explicit future mapping extension and currently stop. The fixture `build_sha` argument tests this binding; it is not a claim that a release migrator ran at the source baseline commit.

Ponytail compromises: package bytes use SQLite BLOB durability in P1 (at most 96 MiB serialized package); production shared CAS, staging/fsync and orphan GC are P2/P3. Authority events use the existing durable outbox with an explicit `authority_command` type; no second scheduler is added and P1 does not dispatch runtime effects. The catalog labels this queue `transactional_pending`. There is a durable 120-new-mutations/minute principal quota and existing HTTP global limiting, not a new distributed rate-limit service. Migrations are trusted local fixture-library entry points, not remotely exposed import endpoints or a production cutover CLI. P3 must supply writer barriers, verified production backup/restore, online batching, release provenance and operator mapping before cutover.
